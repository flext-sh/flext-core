# Add language rules

Treat `$ARGUMENTS` as the requested language and rule scope. Refuse to act when
the language, target project, or required behavior is missing or ambiguous.

1. Read the active project instructions, rule composition mechanism, existing
   language rules, generators, consumers, and canonical validation commands.
2. Search for an existing language owner or narrower rule before creating a new
   artifact. Extend that owner when it already represents the requested fact.
   When the input comes from another rules corpus, classify each statement as a
   mandatory invariant, conditional technology procedure, explicit command, or
   generated projection before adoption; its old file/type is not authority.
3. Define only behavior justified by the detected project toolchain and the
   request. Do not copy rules from another repository or impose framework,
   tracker, orchestration, or private-home conventions on a generic project.
4. Edit the canonical source or generator, then regenerate every owned
   projection. Remove a superseded rule and rewire its consumers in the same
   change; do not retain aliases, fallbacks, or competing policy.
5. Exercise a representative language runtime, then run the project-native
   formatting, lint, type, test, build, security, documentation, and projection
   gates affected by the rule.

Return the selected owner, project evidence that justified the rule, consumers
rewired, exact runtime and gate results, and any unresolved blocker. Missing
tooling or a failed gate is a non-success result.
